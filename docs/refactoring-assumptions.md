# 重构假设说明（V4 专项考核 · 模块十一强制交付物）

> 项目：V2「万能导入解析系统」下单主链路异步事件驱动重构
> 部署：https://0807v4.vercel.app · 仓库：https://github.com/lang430/0506exam

## 1. 为什么选择异步事件驱动，而不是继续同步处理？

V2 原链路在一次请求内完成"解析 → 校验 → 写库"，其成立前提是"文件小、并发低、数据库近在咫尺"。大促场景下三个前提全部失效：

- **请求生命周期约束**：Vercel Serverless 单请求最长 60s（Hobby），10,000 行逐行处理按 200ms/行需要 30 分钟，同步必然超时；
- **资源隔离**：同步模型下每个上传请求都要独占数据库连接到流程结束，多用户并发会迅速打满连接池；
- **失败语义**：同步链路失败即整体失败，用户只能重新上传；异步链路把"接收"与"处理"解耦，部分失败可以精确到行级恢复。

事件驱动（Outbox → 队列 → Worker）进一步带来可恢复性：任务创建与待投递事件同事务落库，任何组件宕机后都能从数据库状态继续，而不是丢消息。

**什么时候同步反而更简单可靠**：单文件 <100 行、单用户低频使用、无进度可视化需求时，同步链路少一层状态机、少一套观测设施，端到端一致性天然成立。V2 的预览编辑工作台（手动改完再提交）就保留了同步提交通道，两条链路并存、各司其职。

## 2. 处理单元大小如何设计，为什么这样设计？

**最终选择：500 行/批**（环境变量 `V4_BATCH_SIZE`，默认 500）。

设计权衡：

- **Vercel Hobby 的硬约束**：虽然 `maxDuration` 可以声明 60s，但 Hobby 计划在 CPU/网络/平台层面经常把函数实例压到约 10s 内被 kill。2500 行/批的 all-or-nothing 事务一旦在写入阶段被 kill，整批回滚并进入 2 分钟"卡死恢复"死循环，监控看板会显示"队列正常 · 待处理 2500 行"；
- **批太小（如 100 行）**：10,000 行拆成 100 个 Job，调度、认领、状态更新、事件写入的固定开销放大 100 倍；且每个批次为保证自包含幂等都要复读整份文件并完整执行规则引擎，解析成本随批次数线性恶化；
- **500 行是 Hobby 下的甜点**：单批解析+校验+写入可在 2~4s 内完成（远低于 10s 硬上限），重试成本可控；10,000 行拆成 20 批，调度端点每轮 8s 可处理 3 批，配合前端 1.5s 轮询内联调度兜底，能在 30~50s 内完成，仍满足 ≤60s 目标。

批次边界用"解析后行号区间 [start_row, end_row)"表达，**最后一批 end_row=-1 为开放区间**：上传期只能预扫描估算行数（表头、空行、矩阵展开都会造成估算偏差），开放区间保证估算偏小时不丢行、偏大时尾部只是空批。

## 3. Worker / Consumer 的容量规划

- **运行形态**：Vercel Serverless，无常驻进程。消费触发路径（三路径互补 + 兜底）：
  1. 上传接口 `after()` 触发 `POST /api/import-dispatcher`（主路径，零延迟启动调度循环）；
  2. 调度端点单轮预算 3 批 / 8s（环境变量 `V4_DISPATCHER_MAX_BATCHES`/`V4_DISPATCHER_BUDGET_MS`），结束时仍有积压则 `after()` 自链续跑；若 after() 因实例挂起未执行，由轮询/cron 兜底；
  3. 任务进度轮询（1.5s/次）在**响应前内联**执行一轮调度（停滞门控：仅无批次正在处理时，预算 1 批 / 2.5s，请求生命周期内必然释放租约，"只要有人看进度就推进"）；
  4. `vercel.json` cron（每日 03:00，`0 3 * * *`）扫描 + 本地 `scripts/worker-loop.mjs` 作为宕机/冻结兜底。
  - 说明：早期版本仅依赖单一 `after()` 后台调度，实测 Hobby 计划的挂起实例会持有调度租约并阻塞后续循环（造成 90s 停滞）。收敛为三路径互补后，`after()` 仍用于上传触发与自链续跑（轻量、非阻塞），但轮询内联路径保证即使 `after()` 挂起也能推进。
- **卡死恢复窗口**：`V4_STUCK_BATCH_SECONDS` 默认 30s（环境变量可调）。批次被 Hobby kill 后，30s 内即会被 `recoverStuckBatches` 回收为 ready 并重试；租约 `V4_DISPATCHER_LEASE_SECONDS` 默认 15s，保证 kill 后新调度器能快速接管，不会出现 2 分钟无人推进的"假队列正常"。
- **并发模型**：**全局单处理器**。`dispatch_lease` 租约表（15s 自动过期 + CAS 抢占 + 循环结束主动释放）保证同一时刻只有一个调度循环在消费。这是实测得出的结论：早期版本允许多实例并行抢批，6 个并行重事务把免费规格数据库直接拖垮、事务超时回滚、批次卡死（详见第 12 节）。串行下单批 2~4s，吞吐余量充足；真正需要并发时按第 12 节的扩展路径走。
- **函数时限**：轮询内联调度预算 2.5s（≤1 批，停滞门控），调度端点预算 8s（≤3 批），均远低于 Hobby 实际约 10s 的硬上限。预算耗尽即优雅退出，剩余批次由下一轮接续——这是无状态设计带来的免费能力。

## 4. 10,000 单/分钟的性能推导

| 推导项 | 数据 |
|---|---|
| 数据量 | 10,000 行压测文件（test-data/10000-orders.xlsx，487KB） |
| 处理单元 | 500 行 × 20 批 + 1 空尾批；批次 = 认领、执行、重试、幂等的最小单元 |
| 并发模型 | 全局单处理器串行（租约锁），Serverless 按需唤起 |
| 数据库压力 | 每实例单例连接（idle 20s 释放）+ 后台独立连接；校验为每批 1 次 IN 查询；写入为 250 行/块的多行 UPSERT，单批 2 次往返 |
| 单批耗时（估算/实测） | 首批：解析 939ms + 规则 134ms + 校验 ~10ms + 写入 ~150ms ≈ 1.3s；缓存命中批：解析/规则 0ms + 校验 ~10ms + 写入 ~120ms ≈ 0.2s |
| 全链路（估算） | 上传返回 ≤1s；调度端点每 8s 处理 3 批 + 轮询每 1.5s 兜底推进 1 批，20 批预计 30~50s，满足 ≤60s 目标 |

**结论**：500 行/批在 Hobby 约束下是稳定性优先的甜点。20 批预计 30~50s 完成，仍满足 10,000 单/分钟（即 60s）目标，且单批远低于 10s 硬上限，不会因 all-or-nothing 事务被 kill 而陷入"队列正常"假死。

## 5. 数据库连接池和 Worker 并发如何控制？

- 每个 Serverless 实例的 postgres 客户端 `max: 1`：单实例任何时刻最多 1 个连接；
- 消费侧由租约锁限制为全局单处理器，写入压力恒定（每批 ~10 次往返，无长事务外的持锁）；
- 上传/查询等短请求各自短连接、用完即弃（Serverless 模型下连接随实例回收）；
- Supabase Pooler（6543 事务模式）承接实例级的连接复用，直连（5432）仅用于本地脚本与 DDL；
- 明确禁止逐行查询/逐行 INSERT（批量 IN 校验 + 250 行块状 UPSERT），从查询数量级上消除连接池压力。

## 6. Outbox 如何避免"任务创建成功但消息丢失"？

- **同事务**：`POST /api/import-tasks` 在**同一个数据库事务**中写入 import_tasks、import_task_files、import_task_batches 和 event_outbox（ImportTaskCreated + N 个 ImportBatchCreated）。事务要么全部可见，要么全部回滚——不存在"任务存在但事件丢失"的中间态；
- **投递状态机**：event_outbox.status ∈ pending → sent / failed，投递失败按指数退避（2^n×5s，上限 300s）重试，retry_count ≥5 转 failed（死信）；
- **宕机恢复**：Dispatcher 无状态，每次从 `status='pending' and next_retry_at <= now()` 重新扫描。"任务已创建但消息未投递"时宕机，恢复后第一轮调度即继续投递（自动化测试场景 3 验证）；
- **重复投递**：event_id 唯一约束防止同一事件重复入表；Worker 侧的幂等（第 7 节）保证即使重复消费也不产生副作用。

## 7. 处理单元 Job 如何做到幂等？

四层防线：

1. **认领互斥**：`FOR UPDATE SKIP LOCKED` 保证同一批次同一时刻只被一个处理器认领；
2. **状态门闩**：批次完成走条件更新 `update ... set status='completed' where id=? and status='processing'`，只有首次转换成功的事务才累计任务进度（processed/success/failed）；重复消费时条件不成立，进度**不会重复累计**；
3. **业务键 UPSERT**：运单写入以稳定 id（`外部编码:SKU编码:行号`，无外部编码时 `任务id:行号`）做 `on conflict (id) do update`——同一行重复写入等价于覆盖，不会重复入库；
4. **错误明细允许重写**：错误表记录随批次事务写入，重复消费前事务未提交则无残留，已提交则批次不再被认领。

自动化测试场景 5 对该语义做了直接验证（强制重放已完成批次：进度与运单数均不变）。

## 8. 部分行失败时为什么允许成功行继续入库？

- **业务价值**：大促导入 10,000 行，170 行有错。若整批回滚，用户要修正 170 行后重新上传并重新等待全量处理；成功行先入库则只需处理失败行（错误明细精确到行号/字段/原始值/修复建议，可导出 CSV 修正后单独再传）；
- **一致性边界**：出库单场景每行是独立的"SKU 发货指令"，行间无事务依赖（收货信息按外部编码聚合只是展示层分组，不要求原子性）；
- **状态如实呈现**：任务终态 partial_success 明确告知"部分入库"，配合失败明细导出，形成"导入 → 定位 → 修正 → 补传"的闭环；
- **风险与对冲**：成功行先入库意味着错误行不会阻断关联行——若业务未来出现"同单必须整单成功"的需求，应把聚合单位从行升级为外部编码组，在批次内按组裁决。当前题面未要求，按行裁决。

## 9. SKU 校验降级的触发条件和风险提示

- **触发条件**：SKU 主数据批量查询超过 `V4_SKU_CHECK_TIMEOUT_MS`（默认 3000ms），或数据库连接短暂失败；
- **降级行为**：跳过 E001（SKU 存在性）校验，保留全部本地格式校验（必填/电话/数量/A/B 组/重复）；
- **不静默**：
  - 任务记录 `import_tasks.degraded = true`，批次记录 `sku_check_skipped = true`；
  - 写入 ImportTaskDegraded trace 事件与批次日志（batch_performance_log.degraded）；
  - 任务详情页顶部固定橙色横幅："⚠️ SKU 校验已降级：本次导入未经过商品主数据完整校验，数据可能需要后续复核"；
- **恢复**：降级是查询级决策（每次 SKU 查询独立计时），服务恢复后新任务/新批次自动恢复正常校验；
- **补校验策略（本次未实现，策略说明）**：对 degraded=true 的任务，可在夜间低峰以任务为单位重跑 E001 校验，把新发现的 E001 行标为"待复核"并通知导入人；实现上复用现有 errors 表与错误码体系，无需新表。

## 10. 错误日志中敏感数据如何脱敏？

- **入口统一**：`maskRawValue(fieldName, value)` 按字段分派——手机号保留前 3 后 4（138****5678）、地址保留前 6 字符（上海市浦东新******）、姓名保留姓氏（张**）、其余字段截断至 200 字符；
- **落库即脱敏**：import_task_errors.raw_value 写入前完成脱敏，数据库与所有展示端（错误列表、Trace 失败节点、CSV 导出）看到的都是脱敏值，不存在"库里明文、前端脱敏"的泄露面；
- **排障与安全的平衡**：保留的错误码 + 行号 + 字段 + 脱敏值足以定位"第几行、哪个字段、什么原因"；确需原始值人工核实的，走原始文件（import_task_files 保留全量上传文件）受控下载通道，而不是在日志里留存明文。

## 11. 压测数据如何生成、如何清理？

- **生成**：`npm run seed`（scripts/seed-data.ts）幂等执行：
  1. 清理上一轮 SKU_ 前缀主数据与 LT 前缀压测运单；
  2. 批量灌入 20,000 条 SKU 主数据（2000/批 UPSERT，约 4s）；
  3. 灌入压测文件专用解析规则（走 parse_rules 配置，不硬编码）；
  4. 生成 10,000 行压测 Excel，其中预埋 120 个非法 SKU（E001）+ 30 个非法电话（E003）+ 20 个非正数量（E004），用于验证错误定位能力。
- **清理策略**：
  - 压测运单：外部编码统一 LT 前缀，loadtest 每轮执行前自动清理（`delete from imported_orders where external_code like 'LT%'`），重跑不产生脏数据；
  - 主数据：SKU_ 前缀，seed 重跑时先删后插，数量恒定 20,000；
  - 运行数据（错误明细/性能日志/trace/Outbox）：按任务级联；`seed --deep` 可清空全部 V4 运行数据；
  - 生产长期运行建议：Outbox 的 sent 记录与 batch_performance_log 按月分区归档（当前规模无需）。

## 12. 如果可以向产品经理或运维团队提问，我会问哪些问题？

**问产品经理**：

1. 同一外部编码在**不同任务**中重复出现时，业务上期望"幂等覆盖"（当前实现）还是"拒绝并报错"？这决定重复检测的口径；
2. 降级的导入数据是否需要自动补校验闭环？补校验发现问题的行，是自动撤回还是仅标记待人工复核？
3. 10,000 单/分钟是峰值均值还是瞬时峰值？如果存在 1 秒内涌入 10,000 行的突发，上传接口需要排队机制吗？

**问运维团队**：

1. 告警接入渠道（钉钉机器人/Webhook）与告警分级标准？当前看板已有橙色积压预警与红色队列不可用告警，只差推送通道；
2. 数据库升配窗口：当前免费规格下"全局单处理器"是保护性设计，若吞吐目标提升 5 倍，需要连接数与 CPU 的预算确认；
3. 审计要求：import_task_files 保留原始文件的周期与访问审计策略。

**架构自问（已验证的答案）**：为什么多 Worker 并发反而更慢？——实测 6 并发抢批时，免费规格数据库在并行重事务下响应劣化，事务超过函数时限被杀、批次卡死；串行单处理器总耗时反而最短。扩容的正确顺序是：先升数据库规格 → 再开受控并发（租约分片，并发度 ≤ 连接池/单批连接数）→ 最后才考虑把解析与写入拆分到不同池。**并发是扩容手段，不是默认正确。**
