## 二、功能需求逐项对照（模块一~十一）

### 模块一：压测数据自动准备（强制） ✅
- 要求：一键脚本、清理旧数据、灌 20,000 条 SKU、生成 10,000 行 Excel、混入非法 SKU、可重复执行、README 说明。
- 实现：`scripts/seed-data.ts`（`npm run seed`）。SKU 20,000 条（`SKU_00001~SKU_20000`）；Excel 10,000 行（2,000 外部编码 × 5 行）；预埋 120 非法 SKU + 30 非法电话 + 20 非正数量 = 170 错误；`LT%` 前缀可重复清理；规则走 `parse_rules` 不硬编码。
- 证据：seed-data.ts、README「压测与验收」。

### 模块二：上传即返回 + 创建异步任务 ✅
- 要求：收文件、生成 task_id/trace_id、存原始文件、预扫总行数、建 import_tasks、建 Outbox、≤1s 返回、前端防重复、去重策略。
- 实现：`app/api/import-tasks/route.ts`。单事务写 文件+任务+批次+Outbox；`preCountRows` zip 级行计数（10k 行 ~26ms）；SHA256 去重（60s 活跃任务复用、24h 提示 duplicate_of）；返回含 `upload_ms`。
- 证据：route.ts、tasks/page.tsx（上传按钮 loading 防重复）。

### 模块三：Outbox 投递与队列入队 ✅
- 要求：任务创建与 Outbox 同事务；Dispatcher 轮询投递；pending/sent/failed；retry_count；宕机可恢复；Worker 幂等。
- 实现：`lib/v4/queue.ts`（`enqueueEvents` 同事务，`dispatchOutbox` 轮询投递、指数退避、≥5 次转死信）；`lib/v4/dispatch.ts`（无状态可恢复）；PG 原生队列（`import_task_batches.status` 即队列体）。
- 证据：queue.ts、dispatch.ts、测试场景 2/3。

### 模块四：Worker 异步处理 ✅
- 要求：读数据→复用规则引擎→批量字段映射→批量 SKU 校验→行级校验→批量 UPSERT→失败行写错误表→性能日志→原子进度→终态聚合（10 步）。
- 实现：`lib/v4/worker.ts`（`processBatch` 完整 10 步）。状态规则 pending/processing/completed/partial_success/failed 全部落地。
- 证据：worker.ts、queue.ts `finalizeTaskIfNeeded`。

### 模块五：处理单元幂等与重复处理保护 ✅
- 要求：同 task_id+unit_id 重复消费不重复入库/不重复累计；状态表记录状态/版本；UPSERT 稳定业务键；重试不重复累计；已完成单元快速返回。
- 实现：四层防线——`FOR UPDATE SKIP LOCKED` 认领互斥 + 状态门闩（条件 `where status='processing'`）+ 业务键 `on conflict(id) do update` + 错误表随事务写。
- 证据：worker.ts `processBatch`、测试场景 5（重放已完成批次：进度/运单数不变）。

### 模块六：精细化错误记录 ✅
- 要求：错误表含批次/行号/字段/脱敏原始值/错误码/原因/修复建议；前端按批次+错误码筛选、分页、点击看详情、可导出；不出现"导入失败请重试"。
- 实现：`import_task_errors` 全字段；`error-codes.ts` E001~E008 + 可读原因 + 建议；`mask.ts` 脱敏；路由支持 batch/error_code 筛选分页；CSV 导出；任务页/跟踪页均展示明细与建议。
- 证据：validate.ts、error-codes.ts、mask.ts、errors/errors-export 路由、tasks/[id]/page.tsx、traces/page.tsx。

### 模块七：任务进度与结果页 ✅
- 要求：展示文件名/task_id/trace_id/状态/总行数/已处理/成功/失败/总批次/已完成批次/吞吐/ETA/最近错误摘要/降级标注/可导出。
- 实现：`tasks/[id]/page.tsx` 全部字段 + 1.5s 轮询（终态停）+ 降级横幅 + CSV 导出。
- 证据：tasks/[id]/page.tsx、GET /api/import-tasks/:taskId。

### 模块八：监控看板 ✅（含加分项）
- 要求 4 区：实时吞吐、队列积压（>1000 橙警/存在卡死批次或不可用红警）、阶段耗时 P50/P95/P99、错误类型分布可跳转。
- 实现：`monitor/page.tsx` + `lib/v4/monitor.ts`。吞吐（近 5 分钟/分钟）、队列积压预警、阶段 P50/P95/P99（`percentile_cont` 真实聚合）、错误分布（可点跳 Trace）。
- 加分：慢批次 TOP10、失败任务趋势、数据库不可用红警（`alertLevel: critical`）。
- 证据：monitor/page.tsx、monitor.ts、import-monitor/summary 路由。

### 模块九：全链路 Trace 检索 ✅
- 要求：按 task_id/trace_id/文件名/批次号/行号范围/错误码检索；时间线展示；失败节点展示批次/行号/字段/脱敏原始值/错误码/原因/规则/阶段耗时/是否重试/下一步。
- 实现：`traces/page.tsx` + `/api/traces`、`/api/traces/:traceId`。多条件检索 → 时间线 + 批次耗时 + 失败节点明细（含规则名、降级标记）。
- 证据：traces/page.tsx、traces 路由。

### 模块十：容灾降级 ✅
- 要求：SKU 查询超时 3s 或 DB 短暂失败→降级（跳过 E001，仅本地格式校验）；前端明确提示；不静默；写入任务/监控日志；记录未校验行；恢复后新任务正常；补校验策略说明。
- 实现：`worker.ts` `withTimeout(..., 3000)` 捕获→`degraded=true`、写 `ImportTaskDegraded` trace、批次 `sku_check_skipped=true`、任务页橙色横幅。假设说明第 9/11 节说明补校验策略。
- 证据：worker.ts、tasks/[id]/page.tsx、测试场景 10。

### 模块十一：《重构假设说明》✅
- 要求 12 点全部覆盖（为何异步、单元大小、容量规划、10k 推导、连接池控制、Outbox 防丢、幂等、部分行入库、降级触发、脱敏、压测生成清理、可提问清单）。
- 实现：`docs/refactoring-assumptions.md` 12 节齐全。
- 证据：refactoring-assumptions.md。

### 本轮二次核验新发现并修复（关键）
5. **🔴 构建阻断回归（TS1010）**：`app/api/import-tasks/[taskId]/route.ts` 第 8 行 JSDoc 缺失闭合 `*/`，导致整个 `GET` 处理函数被吞进注释，`tsc --noEmit` 报错、生产构建必然失败、任务进度轮询接口整体失效。已补回 `*/`，类型检查恢复 0 报错。**此项若漏掉将直接导致部署失败与考点 3/4 全线丢分。**
6. **监控快照漏采吞吐量**：原采集缺 `throughput`（看板四大强制区之首）与 `failedTaskTrend`，且监控接口降级返回 `{alertLevel:"critical"}` 时字段缺失会抛异常导致快照丢失 → 已补全六类字段、新增 `peak_throughput_rows_per_min`，并对全部字段做空值兜底。

8. **压测报告缺「监控看板」章节**：提交物 10.3 明确要求监控看板日志，原报告 8 个章节中无对应内容 → 新增「监控看板证据」章节，含四大区真实读数表（峰值吞吐 ≈55,000 行/分钟、积压 `warn` 预警真实触发并自动恢复、四阶段 P50/P95/P99、E001/E003/E004=120/30/20）及机器可读证据字段说明。

## 七、本轮反向审计与继续开发（2026-08-04）

本轮没有把原有“100 分自评”直接视为验收结论，而是按代码和测试重新核对。发现并修复了三处会影响真实评分的问题：

1. **处理单元幂等补强**：`processBatch` 现在在同一事务内先 `FOR UPDATE` 锁定批次并确认仍为 `processing`，再执行 UPSERT、错误明细和性能日志；强制重放不会重复写入任何三类数据，返回统计也不会虚增。
2. **压测 PASS 判定补强**：`scripts/loadtest.mjs` 现在必须同时满足服务端上传 P95 ≤ 1 秒、全链路 ≤ 60 秒、成功/失败行数准确、无 500/504 才能输出 `PASS`；此前只打印预期行数但未参与判定的问题已修复。
3. **Trace 可靠性补强**：任务创建和 Outbox 投递节点分别写入 `trace_events`，不再完全依赖 `after()` 才能看到首个链路节点；缺少文件/规则的失败批次也保留任务的 `trace_id`。

本轮实证结果：`npm run typecheck` 通过；`npm test` 为 25 项通过、1 项服务未启动跳过；线上 `V4_TEST_BASE_URL=https://0807v4.vercel.app npm test -- tests/v4-http.test.ts` 为 4 项通过；`npm run build` 通过（仅有 Next middleware 弃用和 `pdfjs-dist` external 警告）；需求覆盖、demo 解析和 1000 行性能脚本均通过。

依赖安全复核同步完成：`next` 已升级到 16.3.0，PostCSS override 已升级到 8.5.25，`npm audit` 当前为 0 vulnerabilities。
